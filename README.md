# CheckStock

Складской учёт одного магазина: остатки по ФФ, резерв FBS, перемещения, отправки FBO и история операций.

## Запуск

Нужен Docker с Compose v2.

```sh
docker compose up --build -d
```

Откройте http://localhost:18120. Другой порт можно задать через `CHECKSTOCK_PORT`.
Миграции и начальные приходы выполняются автоматически. Повторный запуск сохраняет данные и не дублирует приходы.

| Артикул | Товар | Север | Юг |
| --- | --- | ---: | ---: |
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Остановка с сохранением данных: `docker compose down`.

## Проверки

```sh
docker compose --profile test run --build --rm test
docker compose --profile test stop test-db
```

Тесты работают с отдельным PostgreSQL, без доступа к рабочим остаткам. Проверяются складские сценарии, повторы запросов, конкурентные операции, ограничения базы, история и входные данные. После каждого теста остатки сверяются с журналом, а весь принятый товар — с остатками, транзитом и завершёнными отправками.

Короткий сценарий на исходных данных:

1. Зарезервировать 4 органайзера на Севере для FBS: на складе 10, свободно 6, резерв 4.
2. Попробовать отправить 7 с Севера по FBO: получить отказ, хотя на Юге есть ещё 6.
3. Переместить 2 с Юга на Север. До приёмки на Юге 4, на Севере 10, между ФФ в пути 2. После приёмки на Севере 12, свободно 8.
4. Отправить резерв FBS: на Севере 8, резерв 0, к клиенту в пути 4. Подтвердить доставку.
5. Отправить 3 с Юга по FBO и подтвердить приёмку: на Юге 1, принято маркетплейсом 3.
6. Удалить Юг: ФФ в архиве, 1 организайзер и 4 корзины остаются на нём. Проверить остатки и историю.

## Устройство учёта

Python 3.13, FastAPI, SQLAlchemy, PostgreSQL 18, Alembic. HTML, CSS и JavaScript без сборки и внешних CDN. HTTP-маршруты, складская логика, запросы и модели разделены в `app/inventory`; интерфейс находится в `app/static`.

`balances` хранит физический остаток и резерв по паре товар/ФФ. Свободное количество вычисляется как разница. `movements` хранит маршрут и состояние операции. `stock_events` — неизменяемый журнал с изменениями остатков и названиями ФФ на момент действия. Триггер запрещает менять и удалять записи журнала.

Изменение остатков, состояния операции, журнала и результата команды происходит в одной транзакции. Строка остатка блокируется через `FOR UPDATE`; подтверждения блокируют саму операцию. Проверки в базе запрещают отрицательные остатки и резерв сверх физического количества. Чтение сводки использует единый снимок `REPEATABLE READ`.

Для изменений API обязателен UUID в заголовке `Idempotency-Key`. Повтор с тем же ключом и данными возвращает сохранённый ответ, с другими данными — 409. Ошибочная транзакция не сохраняет ключ. Повторное подтверждение уже выполненного действия безопасно и с новым ключом. Интерфейс сохраняет ключ при сетевой ошибке, в том числе после перезагрузки вкладки.

Удаление ФФ — архивирование. Остатки, резервы и история остаются на исходном складе. Новые приходы, входящие перемещения, FBS и FBO для архивного ФФ запрещены. Можно переместить свободный остаток на действующий ФФ, принять отправленное ранее перемещение, отправить или отменить существующий резерв.

## Рост нагрузки

Каталог и остатки выдаются страницами по 50 товаров, максимум 100. Поиск выполняется в PostgreSQL с GIN-индексами `pg_trgm`. Навигация использует курсор по уникальному идентификатору, без больших `OFFSET`. История и незавершённые движения тоже ограничены страницами; для последних есть частичный индекс. Сводные остатки считаются в SQL и не зависят от текущего фильтра товаров.

В Compose по умолчанию два рабочих процесса. `WEB_CONCURRENCY`, `DB_POOL_SIZE` и `DB_MAX_OVERFLOW` задают число процессов и лимит подключений каждого процесса. Общий верхний предел подключений приложения: экземпляры × процессы × (размер пула + дополнительные подключения). По умолчанию это 20, плюс соединения миграций и обслуживания. При исчерпании пула API возвращает 503 с возможностью безопасного повтора.

В процессах нет складского состояния или локальных блокировок: несколько экземпляров используют один PostgreSQL, общие ключи команд и блокировки строк. Миграции вынесены в отдельный `setup`. Для нескольких серверов потребуется балансировщик; один PostgreSQL остаётся общей точкой записи. Рост истории сначала проверяется через `EXPLAIN ANALYZE` и метрики запросов. Предрассчитанные сводки, партиционирование и очередь фоновых интеграций стоит вводить при подтверждённой нагрузке; чтение актуальных остатков нельзя безусловно переносить на отстающую реплику или кеш.

## Границы прототипа

Одна операция содержит один артикул и целое количество. Приёмка полная. Отмена FBS доступна до отправки; после отправки доступно подтверждение доставки. Возвраты, частичная приёмка, расхождения, продажи со склада маркетплейса и интеграции API в это задание не входят. Принятые FBO и доставленные FBS показаны накопительно, с товаром и получателем; это не текущий остаток маркетплейса после продаж.

Прототип рассчитан на локальную проверку: веб-порт привязан к loopback, PostgreSQL не публикует порт. Приложение работает без root с файловой системой только для чтения. Есть проверка входных данных, источника запросов и Host, CSP и экранирование пользовательского текста. Пароли в Compose предназначены для локальной демонстрационной базы. Для общего доступа потребуются авторизация, роли, HTTPS, отдельные секреты, резервное копирование и мониторинг.
